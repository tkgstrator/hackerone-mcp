# Report follow-up and submission

The user requested the previously proposed report updates, reply drafts and confirmed submission, followed by a reviewed PR, passing CI, merge, release and local image installation. Existing Rust/rmcp tools and the private persistent drafts volume remain the integration points. This explicit execution request supplies the scope; routine implementation choices below are Codex decisions.

## Approach

Extend the existing typed Hacker API client and local draft store. Keep report comments as local text with a fixed HackerOne report URL: the public Hacker API does not document comment creation, while the Customer API is a different credential surface. Do not introduce browser cookies, undocumented endpoints, generic HTTP tools or a second service.

Submission uses the documented POST https://api.hackerone.com/v1/hackers/reports. A preview and a separate explicit submit call replace the old absolute GET-only policy. Remote submission is disabled unless H1_MCP_ALLOW_SUBMIT=true. Preview tokens bind the account, exact local draft content, revision and destination. A token is a consistency mechanism, not evidence of human approval: instructions require showing the preview and receiving the user's explicit approval before the submit tool is called. This task does not approve sending any real report or comment.

## Tools and behavior

- `report_updates(report_id, mark_seen=true)` fetches one report and compares selected status/time/bounty fields and activities with a persistent account-bound local snapshot. First observation is identified as a baseline, never described as newly arrived. New and edited activity IDs are returned as untrusted data. Missing fields are distinguished from explicit nulls; missing activities never mean no comments. Do not claim complete history beyond activities returned by HackerOne. A failed request or malformed report must not advance the snapshot. `mark_seen=false` previews without advancing.
- `report_reply_draft(report_id, message)` saves bounded, nonempty UTF-8 reply text locally, with a canonical report URL and manual-send guidance. `report_reply_draft_get(report_id)` reads it back after restart. Never posts or opens the browser automatically. These tools work without API credentials.
- `report_submit_prepare(draft_id, expected_revision)` validates the existing draft offline, binds the current account and complete stored draft, saves a private preview record, and returns the exact outgoing JSON, recipient, revision, warnings and confirmation token. Local-only notes/CWE/CVSS/references are not added to the API body. No POST occurs. Missing credentials, invalid/stale drafts and drafts with a prior attempt fail clearly. A new prepare replaces only an unattempted preview, invalidating its token.
- `report_submit(draft_id, expected_revision, confirmation_token, confirm=true)` requires opt-in, credentials, explicit true confirmation, valid current draft and matching account/content/revision/token. Atomically consume and durably persist an `attempting` record before issuing one POST. Repeated/concurrent calls and restart must never cause a second POST for that draft ID. Preview/claim must use the same filesystem lock as draft updates to prevent races. An edit BEFORE claim rejects submission; an edit AFTER claim cannot change the exact serialized preview bytes already claimed. Release the filesystem lock before network I/O and reacquire it only for recording the receipt.
- `report_submission_get(draft_id)` returns the persistent receipt or pending/unknown status without POSTing. Successful valid responses store the returned canonical report ID and fixed report URL. HTTP errors, malformed/oversized success responses, timeout, disconnect, interrupted process or inability to persist a receipt leave the attempt consumed and explicitly uncertain/failed; never automatically retry or expose raw response/request bodies. Users must inspect HackerOne before any manual new submission. No reset/retry tool is provided.

## Persistence and HTTP constraints

Use private, bounded JSON records inside the existing 0700 drafts directory under reserved dot-prefixed names, 0600 files, O_NOFOLLOW/nonblocking reads, regular-file/owner/mode checks, existing cross-process lock, atomic replacement and file + directory fsync for the claim. Any durable-write failure prevents POST. Draft deletion must not delete the attempt ledger. The existing draft list ignores the records. Corruption fails closed. No new runtime service or dependency is needed.

Records are limited to 8 MiB; snapshots retain up to 1000 observed full activity objects, keyed by canonical ID and compared by JSON equality. Exceeding either bound fails clearly without advancing, rather than silently evicting observations. Account usernames are stored inside private records, never file names. Load the prior snapshot before fetching and compare it under the lock before saving (optimistic concurrency); a concurrent baseline change fails rather than regressing the cursor. Missing selected fields retain the previous observation and are reported as unavailable. In particular an omitted activity array must not remove old IDs. Bounties and selected status/time fields follow the same missing-vs-null rule.

Reuse src/draft/validate.rs's existing payload mapping: impact comes from Draft.impact, required strings must be nonblank, body and fields use current model limits, team_handle also passes client::validate_handle. Optional severity/weakness/scope IDs map directly. Retain exact compact serialized JSON bytes in the preview and send those bytes. The ledger stores the complete Stored draft (or equivalent Draft + body fields) for equality checks; it does not need a content hash dependency. Deleting/recreating the SAME draft ID cannot bypass a prior attempt. Copying to a DIFFERENT draft ID is outside the suppression guarantee and is explicitly warned against for uncertain results; do not claim server-side or cross-ID idempotency. Local draft editing/deletion remains allowed and never changes the receipt. After any failed attempt, inspect HackerOne manually; only after confirming non-creation may the user fix a local draft and deliberately create a new ID. There is no automatic recovery POST.

Parse H1_MCP_ALLOW_SUBMIT as unset/empty/false => disabled, exact true => enabled; reject other strings such as TRUE and 1. rmcp 3.8.0 supports annotations: report_submit has read_only_hint=false, destructive_hint=true, idempotent_hint=false, open_world_hint=true. The confirmation token is an unpredictable preview identifier, not a secret or human-approval credential. Use strong OS randomness for preview identifiers and fail on entropy errors rather than accepting the draft model's fallback randomness.

Use a separate POST reqwest client with `.retry(reqwest::retry::never())` in addition to exactly one send call: locked reqwest 0.13.5 can otherwise retry protocol NACKs internally. Preserve the existing GET client policy. Tests for snapshot concurrency must include two observations completing in reverse order; optimistic baseline comparison rejects the stale second write.

After claim, perform the already-authorized one-shot send and receipt recording in a spawned task that survives cancellation of the waiting handler while the server stays alive. Process death still leaves attempting/unknown and blocks replay. Test handler cancellation separately from process interruption. Receipt failures must preserve consumed state and report any known accepted report ID safely; they must never trigger another POST.

Keep all HTTP in src/client with the fixed production origin, redirect denial, existing timeout and 4 MiB response limits. GET retry behavior is unchanged. POST has exactly one send and no retry on any status or transport failure; suppress raw API error text for POST because it can echo confidential report content. Use the same public report ID validation. Mark submission as non-idempotent/destructive/open-world in MCP annotations when supported. Never infer triage, acceptance or payment from absent fields. Treat all report/draft/comment text as untrusted.

## Release and acceptance

Bump to 0.4.0, update README/server guidance/Docker metadata/guard and stdio/smoke tool inventories consistently (21 tools). No dependency changes. Retain local-only behavior of existing draft tools and explain explicit remote submission opt-in. Local configuration will enable the requested submit capability after installing the immutable released image; no actual POST is part of installation verification.

Tests cover snapshot baseline/new/edited/missing fields/restart/account separation, reply bounds/persistence/path rejection, submission no-network preconditions, exact POST payload/path, one-send errors including 429/5xx/redirect/invalid JSON, stale previews, concurrency/restart/deleted draft ledger, corruption/symlinks/permissions and durable claim behavior. Use mock HTTP for POST, never the user's real report or token. Run native cargo test/fmt/clippy plus all required PR CI gates. Fresh independent actual-diff review precedes merge; verify released digest/platforms and local stdio tools/API GETs, then clean only owned disposable resources.
